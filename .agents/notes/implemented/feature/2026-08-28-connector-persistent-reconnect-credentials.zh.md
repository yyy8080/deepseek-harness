# Agent Note: Persistent, non-expiring connector reconnect credentials

Status: implemented

[English](2026-08-28-connector-persistent-reconnect-credentials.md) | 中文

## Problem

一位用户在「设置 → 连接器」里登记了一台机器、运行了 pack，并希望这台机器保持可用：在笔记本休眠、网络切换或部署重启之后能自己重新连接，而不必每次都重新下载一份新的 pack。用户的原话是「连接器的密钥永远不会过期，这样可以让机器掉线了后续还能自己重新连接」。

挡在前面的有两件事，而其中只有一件真的关乎密钥的寿命。

接入路径从不让 token 过期：`admitAttach` 按 id 找到登记记录并比较其密钥，没有任何时限。下载窗口的 `packTtlMs`（当时是 30 分钟）只关掉 `claimDownload`——即脚本文件的重新抓取——而账本会在该窗口过后把机器报成 `expired`。于是 UI 告诉用户密钥已过期，可机器其实仍能重新连接。寿命是被误报了，而非真的短。

密钥账本只存在内存里。harness 重启——更尖锐地说，插件重载，一个部署改写自己的组合就会触发它——会丢弃每一条登记记录。此后 agent 的重试循环带着重启后部署从没听说过的密钥拨回来，被永久 `403` 拒绝，直到有人签发新的 pack。这才是「部署重启后还能自己重连」真正的拦路石。

## Decision

一条登记记录铸出一份**按机器、永不过期的重连密钥**，它**能熬过重启与重载**，只能由用户吊销。

**不过期，且如实呈现。** `packTtlMs` 现在默认 `0`，表示 pack 下载一直有效直到该登记记录被移除；取正值仍会作为一项安全选项关掉下载窗口，而无论取何值，它都只管脚本文件的重新抓取，从不管重连。`ConnectorEnrollment.expiresAt` 与 `ConnectorPackTicket.expiresAt` 变成 `number | null`，`null` 表示「下载永不关闭」。机器的 `expired` 状态被移除——一份密钥只会是 `issued`、`downloaded` 或 `attached`，并一直存在直到被移除。连接器页面在每台已登记机器上显示一个永久的「永久有效 · 可重连 / Never expires · auto-reconnect」标记；对不过期的 pack，则用一句「机器会用同一密钥重连直到被移除」替换掉下载截止时间那一行。

**持久的密钥集合。** `ConnectorEnrollmentStore`（`src/store.ts`）把每条登记记录的持久部分——id、密钥、目标系统族、签发时间——写入 `storePath` 处的 JSON 文档，默认位于 harness 主目录下的 `connectors/enrollments.json`（经 `@deepseek-ai/dsh-home-paths` 解析）。`issue` 与 `revoke` 现在是异步的，会在返回前持久化新的集合，方式是跨进程写锁下的原子替换（`@deepseek-ai/dsh-atomic-write`），属主可读（`0600` 文件，位于 `0700` 目录下）。该集合在插件构造函数中同步恢复，早于任何路由回应，因此一台在部署刚起来那一刻拨入的目标会用同一密钥被准入，而不是被当作未知拒绝。构建读不懂的存储文件——非 JSON 字节、类型错误的成员，或未知的 `STORE_VERSION`——会在加载时报错，而不是空着启动，因为悄悄的空账本等于一次性吊销每一台已登记的机器。

**只有密钥是持久的。** 活跃的接入是一条 socket 及其 `ctx.connectors` 注册；没有哪个进程能带着它们熬过重启。agent 既有的重试循环（`runConnectorAttachment`，未改动）会在部署恢复后重新拨入并重新接入。`downloadedAt` 与 `attachGeneration` 是进程内的细化状态，不被持久化；下载截止时间在加载时由 `issuedAt` 与当前的 `packTtlMs` 重新算出。

## Store format

```json
{ "version": 1, "enrollments": [ { "id": "…", "secret": "…", "os": "linux", "issuedAt": 1724832000000 } ] }
```

`STORE_VERSION` 单调递增，未知即拒绝，与本仓库对后端的立场一致（在发布前窗口里拒绝旧的磁盘格式，而不是悄悄迁移）。密钥在磁盘上留存，这就是下文记下的安全代价。

## Security model

重连密钥是对运行过 pack 的机器的一份长期读/写/命令执行能力。让它不过期，意味着泄漏的 pack 或被攻陷的目标机器会一直可用，直到该登记记录被移除——没有轮换，也没有按机器的时限。这是有意为之：无人值守的重连正是本功能。控制手段是：

- **按机器的密钥，而非共享的部署级密钥。** 每条登记记录持有各自的 24 字节密钥，因此 `revoke`（设置 → 连接器 → 移除）只吊销一台机器：断开它的 socket，并在之后每次拨入时拒绝它的 id。用户依赖的保证是吊销，而非过期。
- **存储文件与 harness 主目录同等敏感。** 它保存每台机器的密钥；能读到该文件的人即可冒充每台已登记机器的拨入。属主可读的权限与 harness 主目录自身的保护就是这道边界的全部。
- **下载仍可设界。** 想要旧的短命 pack 链接的部署可把 `packTtlMs` 设为正值；那只收窄脚本的重新抓取，从不收窄它所授权的重连。

## Alternatives considered

**把密钥留在内存里，只是把重试与重签发的循环拉长。** 这让重启这道坎原封不动——目标机器在一次重载后仍会死掉、仍需新的 pack。它回答不了用户的诉求；只有持久化才能让机器在重启后自己重连。

**轮换或过期的重连 token。** 孤立看更稳妥，但它重新引入了用户想要移除的那个过期：一台离线超过窗口的机器就再也无法无人值守地重连，而这正是全部意义所在。吊销在不破坏无人值守重连的前提下给出了同样的「让它停止工作」的控制，所以过期换不来本功能能保留的任何东西。

**通过 settings-file 那条缝来持久化，而不是专用存储。** settings provider 是一份热重载、保留注释、可由用户手改的文档；密钥账本是机器写入、承载密钥、从不手改的。把密钥塞进 `settings.yaml` 会扩大那份文档的暴露面，并把两种无关的写入节奏耦合在一起。一个小而专用的存储复用了同样的原子写与锁原语，却没有这两项代价。

**把活跃接入（标签、工作目录、接入时间）也持久化，好让账本在重启后仍读作「已连接」。** 作为谎言被否决：socket 在重启时已经没了，绑定到「已连接」那一行的会话会在第一次工具调用时失败。诚实的状态是密钥存活、agent 重新拨入，这正是账本现在所报告的。

**放飞持久化写入，立刻返回票据。** 被否决：在崩溃前最后一刻登记的机器会丢失，而存储写入正是「这台机器现在能重连」的提交点。`issue`/`revoke` 会等待它，符合本仓库「在提交点才发布」的规则。

## Testing

`tests/store.spec.ts` 覆盖往返以及每一条报错拒绝路径（非 JSON、根类型错误、未知版本、缺少数组，以及各个畸形成员字段）。`tests/enrollment.spec.ts` 覆盖不过期的下载窗口、用同一密钥从持久记录恢复后的准入，以及持久部分的快照。`tests/portal.spec.ts` 让一个真实 agent 走过组装好的入口，拆掉该部署，再对同一个 `storePath` 拉起第二个部署，并断言恢复出的登记记录会再次准入同一个 agent、而被吊销的那条保持消失。`ui-settings-connectors` 组件测试覆盖永久票据提示与重连标记。

## Consequences

一台一直在跑的目标机器会自己熬过笔记本休眠、网络切换、harness 重启与插件重载并重新连接，无需新的 pack——正是用户要的行为。账本不再把一台可重连的机器误报成已过期。

代价是一份无界、留存于磁盘、按机器的远程执行密钥，其唯一的关闭开关是吊销。入口 README 的威胁模型与「已知限制」现在把这一点直说清楚：重连密钥不会自行过期，而重启丢掉的是活跃 socket（不是密钥），随后 agent 会重新拨入。[426 接入 note](../bug-fix/2026-08-28-connector-attach-lost-upgrade.zh.md) 记下的 `connectors.default` 重载隐患被收窄了——登记记录现在能熬过重载；只有它的活跃 socket 会掉，agent 会重新接入。
