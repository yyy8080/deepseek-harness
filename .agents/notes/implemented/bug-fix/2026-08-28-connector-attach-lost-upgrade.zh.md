# Agent Note: 用 426 回应丢了升级头的连接器拨入

Status: implemented

[English](2026-08-28-connector-attach-lost-upgrade.md) | 中文

## Problem

一位用户对着明文 HTTP 的测试部署跑起连接器 pack，随后看着 agent 失败：

```
dsh-connector: serving /workspace to http://119.45.184.191/connector/attach
dsh-connector-agent dialling http://119.45.184.191/connector/attach (linux, workdir /workspace)
```

每一次拨入都被 `404` 挡回。路由是注册着的，反向代理带着 `Upgrade` 与 `Connection` 转发了该前缀，同一台机器上拨 `127.0.0.1:3082` 的 agent 一次就接上了——部署这边找不出任何缺失。

`Upgrade` 与 `Connection` 都是逐跳头，而 agent 出网路径上的一个透明代理正在从明文 HTTP 请求里删掉这两个头。部署侧的抓包显示，拨入到达 nginx 时头已经没了，而同一台主机上走 TLS 的同一个请求则原样抵达。于是 node 从不抛出 `upgrade` 事件：请求落进入口那个普通的前缀处理器，它只认得 `/agent.mjs` 与 `/pack/<id>`，其余一律——包括它自己的接入路径——回 `404 not found`。

问题全在这个状态码上。`404` 说的是本部署不提供这个路径，于是排查被带向已部署的 SHA、nginx location 与路由注册。真正要紧的那一条事实——请求在途中丢了升级头——恰恰无人报告。

## Decision

`<basePath>/attach` 是入口自己拥有的路径，因此落到这里的普通请求就按它本来的样子回应：`426 Upgrade Required`，带上该状态要求的 `Upgrade: dsh-connector` 头，正文同时点明成因与对策——明文 HTTP 上有中间设备剥掉了逐跳头，改拨 `https` 源，让连接端到端穿过去。

正文的长度是照着 `runConnectorAttachment` 打印拒绝正文的那 200 个字符裁的：需要这份诊断的运维读到它的地方，是目标机器上 agent 自己的输出，而不是部署的日志。

准入本身分毫未动：完整抵达的升级照旧被准入或拒绝，异种升级协议照旧被直接丢弃、不予回应。

## Alternatives considered

**把连接器协议换到一种能穿过这类代理的传输上。** 两条按登记记录配对的半双工 HTTP 流，可以穿过任何转发分块正文的中间设备。本次修复否决了它：那是又一套需要定义、版本化并与升级路径保持同步的传输，而引出这份报告的部署本身已经发布了可用的 TLS 源。426 把那个源指为答案，这才让"推迟该传输"是坦白的，而不是默不作声的。

**只改部署。** 把入口发布到 `https` 上能解开这一位用户，却把下一位留在自己的明文 HTTP 主机上继续读 `404`。部署改动与状态码改动回答的是这份报告的两半。

**回 `400`。** 它准确，但什么也没说。`426` 正是 HTTP 为这一情形定义的状态——请求本身合法，只是服务端要求升级——而它强制携带的 `Upgrade` 头无需赘述就说清了是哪个协议。

**靠连接器 token 头而不是路径来判定升级被剥离。** 否决：那样只会对仍带着 token 的请求回 `426`，而一个可以随手丢掉逐跳头的代理同样可以丢掉别的头。路径本身才是可靠信号，浏览器撞上来时得到的也是同一个真话。

## Verification

`packages/host/connector-portal/tests/portal.spec.ts` 让真实的 agent 循环穿过一个"转发一切、唯独不转发逐跳升级"的代理去打真实的入口，并断言运维看到的报告完整带有 `HTTP 426` 与那条对策——这条消息是照着截断长度裁的，于是截断被真正走了一遍，而不是被假定。另一条测试钉住被剥离拨入的状态码与 `Upgrade` 响应头，而原有的 `404` 用例继续覆盖入口并不拥有的那些路径。

在引出这份报告的那套部署上，明文 HTTP 的拨入如今打印出这份诊断而不再是 `404`；同一份 pack 指向该部署的 TLS 源后，从当初拨失败的同一台机器、同一个网络接入成功，并回应了测活探测。把连接器前缀发布到 TLS 源上、并将入口的 `publicOrigin` 钉到那里，正是让消息所指的那条对策在此可用的前提。

那套部署还顺带暴露了一条接入的寿命有多短：它把已接入的机器钉为组合里的 `connectors.default`，而写下这个钉子会重载本插件，于是刚刚写下其 id 的那条接入被一并丢掉。入口 README 的"已知限制"如今把重载也列为内存账本熬不过的一件事。

## Consequences

接不上的连接器，如今会在那台接不上的机器上说明原因。这一改动没有解决的剩余失败，是一台根本没有任何 `https` 源可达的目标机器；它依旧接不上，只是现在读到的消息如实这么说，而不是去怪端点不存在。
